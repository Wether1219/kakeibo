## 1. 開発環境構築手順

### 1.1 必要ソフトウェア

| ソフトウェア | 用途 |
|---|---|
| VS Code | 統合開発環境 |
| VS Code拡張：ESLint / Prettier | コード整形 |
| VS Code拡張：MySQL（例：cweijan.vscode-mysql-client2） | DBをVS Code内から確認 |
| Node.js LTS | フロント／バックエンド実行環境 |
| Docker Desktop | MySQLをローカルコンテナで起動（環境差異排除） |
| Git / GitHub CLI（任意） | バージョン管理 |
| Claude Code（VS Code拡張 or CLI） | バイブコーディングのエージェント |

### 1.2 MySQL起動（Docker Compose例）

```yaml
# docker-compose.yml
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: kakeibo
      MYSQL_USER: kakeibo_user
      MYSQL_PASSWORD: kakeibo_pass
    ports:
      - "3306:3306"
    volumes:
      - db_data:/var/lib/mysql
volumes:
  db_data:
```

### 1.3 GitHubリポジトリ初期設定

1. プライベートリポジトリを作成（例：`kakeibo-app`）。
2. `main`ブランチを保護（直接pushではなくPRベースを推奨。個人開発でも履歴を残す意味で有用）。
3. `.gitignore`に`node_modules/`、`.env`、DBダンプファイル等を追加。
4. `docs/`配下に本ドキュメント一式（01〜04）を格納し、Claude Code等のAIエージェントに常時参照させる。

## 3. 開発の進め方（バイブコーディング運用方針）

### 3.1 基本方針

- 本ドキュメント（`docs/`配下）をAIコーディングエージェント（Claude Code等）に読み込ませたうえで実装を依頼する。エージェントには「詳細設計書のテーブル定義・API設計に従うこと」を明示的に指示する。
- 1機能（例：F03 取引入力）単位でブランチを切り、①DBマイグレーション → ②API実装 → ③フロント実装 → ④動作確認、の順でAIに段階的に依頼する。一度に全機能を依頼すると設計との乖離やテスト漏れが起きやすいため避ける。
- Excel数式に相当するロジック（5章の按分・週次判定・比率計算）は特にバグが混入しやすいため、実装後に現行Excelの実績値と突合するテスト（3.3節）を必須とする。

### 3.2 Gitブランチ運用

- `main`：常にデプロイ可能な状態を維持
- `feature/f03-transaction-input`のように機能IDを含んだブランチ名を使用
- コミットメッセージ規約（例）：`feat: 取引入力APIを実装 (F03)` / `fix: 週次判定のバグ修正` / `docs: 詳細設計書を更新`

### 3.3 テスト方針

| テスト種別 | 内容 |
|---|---|
| 単体テスト | 5章の集計ロジック（按分・週次判定・比率計算）は必ず単体テストを書く。境界値（端数、0件、分母0）を重点的にカバー |
| 結合テスト | API単位でリクエスト/レスポンスを検証 |
| 移行検証 | Excel移行後、年間推移・収支可視化の数値が現行Excelと一致することを手動突合 |
| 受け入れ確認 | 要件定義書5章の機能一覧に対して、実際にスマホ・PCから操作して消し込み |

## 5. リリース・運用方針

- 個人利用〜小規模世帯利用のため、初期は自宅サーバーまたは安価なVPS/PaaS（例：Railway、Render等）へのデプロイを想定。
- MySQLの日次バックアップ（`mysqldump`をcron等でローカル/クラウドストレージへ）を運用開始時点で必ず設定する。
- `docs/`配下のドキュメントは実装が進むにつれて生じる設計変更を都度反映し、常に実装と一致させる（AIエージェントへの再入力の精度を保つため）。
